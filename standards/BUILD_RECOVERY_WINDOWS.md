# RGNES — Windows x64 CLAP/VST3 build and repair toolkit

**Status:** toolchain procedure, **not** a statement that all user projects can currently compile. A missing project-specific build script, proprietary resource, SDK, or successful Windows CI run blocks release. Do not manufacture a `.clap` or `.vst3` by renaming an unrelated DLL.

## What is provided

- `tools/rgnes_win64_build.ps1` — build launcher for existing `Build_Windows_x64.ps1`, Visual Studio 2022/CMake, or unambiguous MSBuild `.sln`; checks that the requested output was refreshed, extracts ZIP / 7-Zip volumes, runs format verification, and stages runtime-only files.
- `tools/rgnes_verify_win64.py` — portable, no-dependency static check of PE32+ AMD64 binaries, required `clap_entry` and `GetPluginFactory` exports, Steinberg-style Windows VST3 bundle layout, SHA-256 hashes, and a JSON evidence manifest. **It cannot prove that a host will load or process audio correctly.**
- `tools/test_rgnes_verify_win64.py` — synthetic-header tests for positive, wrong-machine, missing-export, and unbundled-VST3 cases. Synthetic fixtures are **not** compiled plugin validation.
- `.github/workflows/rgnes-win64-build.yml` — opt-in Windows GitHub Actions `workflow_dispatch` runner. Select the existing branch/project and actual build artifact path; it cannot build absent source.

### Internal build (Windows 10/11, x64)

Install the **Desktop development with C++** workload in Visual Studio 2022 Build Tools or Visual Studio 2022, the Windows 10/11 SDK, CMake and Python 3.9+. Ensure project-specific CLAP/VST3 SDK headers and libraries, binary resources, generated sample banks and license declarations are present. Use the matching toolchain required by the source. Run in PowerShell:

```powershell
# Example: invoke a project that actually has Build_Windows_x64.ps1
powershell -NoProfile -ExecutionPolicy Bypass -File .\standards\tools\rgnes_win64_build.ps1 `
  -ProjectRoot .\Albedo-Quintessential-Synth `
  -BuildMode PowerShell -ArtifactPath .\Albedo_Quintessential_Synth_Windows_x64_CP11.zip `
  -Formats 'clap,vst3'

# CMake project alternative (requires CMakeLists.txt):
powershell -NoProfile -ExecutionPolicy Bypass -File .\standards\tools\rgnes_win64_build.ps1 `
  -ProjectRoot .\MyPlugin -BuildMode CMake -ArtifactPath .\dist_windows_x64 `
  -Formats 'clap,vst3'
```

`ArtifactPath` is relative to **ProjectRoot**, not the repository root. It must reference **newly produced** plugin binaries, a fresh runtime ZIP or all parts of a `.7z.001` release. The existing CMake config or project script is responsible for copying the installable output into that location. If the build script reports success without updating it, the freshness gate fails.

### External Windows build — GitHub Actions

In the repository's **Actions** tab, select **RGNES Windows CLAP + VST3 Build Gate**, choose **Run workflow**, select a branch with the actual source and enter:

- `project_path`: repo-relative directory containing a real `CMakeLists.txt`, Windows build script or `.sln`.
- `artifact_path`: project-relative output directory, ZIP or `.7z.001` generated by that build.
- `build_mode`: `Auto`, `PowerShell`, `CMake` or `MSBuild`.
- `formats`: `clap,vst3` when both are required, or explicitly `clap` / `vst3` for a single-format project.

The job uses `windows-2022` and checks its own launcher tests before building. If compilation or validation fails, the workflow stops and does not mark release success. On success, it uploads the verified binaries + report as a **temporary GitHub Actions artifact**, not a Git-history commit and **not** an automatic Drive upload. GitHub Actions cannot access the private ChatGPT Library. The upload from build runner to Google Drive requires a configured, authorized transfer integration; never include Drive credentials in source or chat.

## Fault-isolation and recovery order

| Failure | Inspect / fix | Verification after repair |
| --- | --- | --- |
| Build tool missing | Install Visual Studio C++ workload + Windows SDK + CMake, or switch to `windows-2022` CI; record exact compiler and target | CMake configure & compile fresh x64 output |
| Source or generated data missing | Locate approved revision and license-compatible exact audio banks / bitmap resources; regenerate reproducible tables, preserve hashes | Compare source/resource SHA-256; never silently replace audio with placeholders |
| CLAP ABI missing or `clap_entry` not exported | Confirm CLAP headers, `extern "C"`, DLL export visibility, entrypoint and descriptor ID | PE64 export check; CLAP validator when available; plugin scan |
| VST3 SDK, class ID, or `GetPluginFactory` missing | Obtain correct Steinberg VST3 SDK or project-supported bindings; check VST3 factory/exports, 64-bit build and Windows bundle location | PE64 export + bundle check; VST3 Validator when available; plugin scan |
| Undefined symbols, wrong linkage/architecture | Align x64 flags and CRT/compiler ABI, check Windows import libs, generated symbols, resources and SDK version | Clean configure, link, and PE64 machine/export checks |
| DLL created but GUI blank / host rejects | Inspect Windows ABI structs/entrypoint, host window parenting, DPI, resources and saved plugin IDs; use existing rollback | Load/unload/reload in Windows Bitwig; GUI & automation tests |
| Audible crackles, freezes, note dropouts | Separate DSP and GUI workloads, test callback locks/allocations, resampling, rapid automation, polyphony and sample rates | Offline audio stress **and** host realtime QA; no "Hi-Fi" certification from compile alone |
| Archive corrupt / extraction fails | Verify every `.7z.001` to `.NNN` volume in one folder, checksum entire set, extract from `.001` | Full extract, binary SHA-256 and PE/exports check before Drive upload |
| CLAP compiles but VST3 fails | Preserve working CLAP, isolate VST3 wrapper/SDK and own state/parameter bridge; do not rename CLAP into VST3 | Separate VST3 build, export, bundle and host validation |

**Recovery policy:** collect the full build log, failing command, OS/compiler, revision, missing resource, reproducible test, minimum repair, successful clean rebuild and rollback pointer. Fix the root cause before changing unrelated DSP or GUI. If a native build is impossible in ChatGPT's current execution environment, switch to an available **authorized external Windows builder**. If none is available, output the runnable build recipe and label the release **blocked**, not compiled.

## Release acceptance and routing

A release for Windows x64 containing both formats requires **both** binaries to pass independent compilation, PE/export checks and packaging. That is only the `compiled/static-validated` tier. `offline-DSP-tested`, `in-host-tested`, and `user-confirmed` are additional independent gates. Keep stable plugin/parameter IDs and record dates, versions, hashes and source commits. Store source/build scripts/tests/reports on GitHub; only installable runtime distribution on Google Drive when supported and verified. Keep prior known-good rollbacks.

### Known repository limitations during preparation

- The GitHub repository contains an existing `.github/workflows/albedo-cp11-windows.yml` Windows job, but its target branch and resources must exist in that branch before it can pass. A workflow file is not proof of a successful run.
- Rubedo's repository README documents a large external embedded sample bank and other generated resources absent from a plain checkout. These must be supplied/verified before a fresh build; do not inject substitute samples.
